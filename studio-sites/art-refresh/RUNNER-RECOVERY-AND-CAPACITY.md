## 1. Current evidence and decision

Observed GitHub Actions startup failures include runs with `startup_failure`, zero jobs, and no job logs. That is a pre-job dispatch/startup failure; it is not evidence that the registry validator failed. Previous retry attempts were rejected because the startup-failed runs had no eligible failed jobs to retry.

Before purchasing a larger hosted runner, have an organization/repository administrator check:
- GitHub Actions service/incident status and organization/repository Actions policies.
- Hosted runner availability and included/minute quota, billing budget, payment status, and spending limits.
- Runner groups, repository access, required labels, and any enterprise policy inheritance.
- Whether this repository is eligible to use larger hosted runners and what machine sizes are offered in its account/organization.

Do not assume a larger runner fixes a zero-job startup failure. Larger hosted runners primarily change compute capacity; first prove the failure is caused by capacity or machine resources.

## 2. Runner options and provisioning checklist

### Option A — standard GitHub-hosted runner
Use the existing hosted runner class after an administrator confirms Actions policy, quota, and service availability. Keep the art validator job small and deterministic.

### Option B — larger GitHub-hosted runner
1. Administrator opens the organization/enterprise Actions runner settings and confirms larger-runner availability and permitted repository access.
2. Record the proposed size, architecture, included concurrency, per-minute price, storage/network constraints, and budget owner before enabling it.
3. Get explicit budget approval before changing billing or purchasing capacity.
4. Start with a non-production validation workflow; do not grant deployment secrets or production environments.
5. Verify the job actually starts, records a runner name/ID, instantiates steps, runs the sentinel, and uploads logs/artifacts.
6. Compare actual usage against the budget. Larger runner availability and billing vary by account and organization; do not assume it is enabled.

### Option C — self-hosted runner
1. Choose a controlled host or cloud VM with a supported OS, patched packages, Node.js version required by the repo, and adequate disk/RAM.
2. In repository or organization Settings → Actions → Runners, add a runner and download the installer using the instructions generated by GitHub for that exact repository/organization. Do not reuse an old registration token or paste one into this repository.
3. Register it with labels matching the workflow, currently expected to include `self-hosted`, `linux`, `x64`, and `lingo-g02` if that runner label scheme is retained.
4. Install/run the runner service so it actively polls GitHub. An online/idle label alone does not prove a job is dispatched.
5. Verify repository access and runner-group eligibility; use an ephemeral runner for disposable or autoscaled hosts where practical.
6. Run a harmless sentinel job and capture runner name/ID, assigned job, step output, logs, and artifact.
7. Keep production credentials off the runner until the required security review is accepted.

## 3. New workflow requirements

The art registry workflow should be validation-only and least-privilege:
- Trigger on pull requests touching `studio-sites/art-refresh/**`, the relevant game specs, or the workflow itself; support manual dispatch for diagnostics where policy permits.
- Set explicit minimal permissions, normally `contents: read`.
- Pin/setup the Node.js version intentionally and use `npm`/Node built-ins only if no dependencies are needed.
- Run `node studio-sites/art-refresh/validate-registry.mjs` from repository root.
- Emit the commit SHA, Node version, command, exit code, concise summary, and complete failure output.
- Upload logs/report artifacts even on failure where the runner reached the steps.
- Include a first-step sentinel so dispatch, runner assignment, step initialization, and log generation can be distinguished from validator failure.
- Do not expose secrets, use `pull_request_target` with untrusted checkout code, or grant deployment permissions.
- A green independent CI run is useful evidence but does not make GitHub Actions or branch-protection gates pass unless the repository administrator explicitly changes policy and documents that decision.

## 4. Host, bots, API tokens, and secrets inventory

No token values belong in this runbook, issues, commits, workflow logs, or chat. Store only secret names, owner, purpose, scope, rotation date, and verification status.

| Credential class | Required handling |
|---|---|
| GitHub bot / GitHub App | Prefer a GitHub App or short-lived installation token with only required repository permissions; do not use a personal access token as a permanent bot credential unless approved. |
| CI host / cloud VM | Use host identity or secret manager; restrict SSH/admin access, patch host, audit logs, and remove credentials from shell history. |
| Vercel / preview host | Separate preview from production credentials; verify project/team access and environment scope. |
| Cloudflare | Use narrowly scoped API tokens; separate DNS/Workers permissions from account-wide access. |
| Firebase | Use environment-specific credentials; never commit service-account keys or real API secrets. Firebase web config values are not equivalent to private service-account credentials, but placeholder config must still be replaced before acceptance. |
| Other automation bots | Identify owner, scope, expiration/rotation policy, last use, and revocation route; disable unknown or unused tokens. |

For every host/bot/token record: `owner`, `purpose`, `scope`, `environment`, `stored-in`, `last-rotated`, `expiry`, `rotation-owner`, `verified-by`. Record secret *names and metadata only*, never values. Rotate any credential found in logs, commits, artifacts, or shared documents.

## 5. Billing, quota, and capacity register

Record the following from the authoritative GitHub organization/repository billing pages and each connected provider:
- Current plan and billing owner.
- Actions included minutes, consumed minutes, remaining quota, overage/spending limit, payment status, and reset date.
- Hosted-runner concurrency limit and actual active jobs.
- Larger-runner eligibility, machine sizes, per-minute rates, and approval status.
- Self-hosted host/VM monthly cost, uptime, storage, and maintenance owner.
- AppDeploy deployment quota (previously reported exhausted at 125/125 lifetime deployments; re-check before relying on it).
- Vercel team/project access and billing status.
- Cloudflare Workers/Pages limits and any paid resource requirements.

Never include payment-card details or secret tokens in Git. Do not upgrade or increase spending until an administrator confirms that quota/capacity is the cause rather than a pre-job startup failure.

- [ ] Run URL and exact commit SHA.
- [ ] Runner ID greater than zero and runner name populated.
- [ ] Job assigned and steps instantiated.
- [ ] Sentinel step executes.
- [ ] Logs are retrievable and artifact/report is attached.
- [ ] Actual registry validator exits 0 and prints its summary.
- [ ] Required GitHub branch-protection checks pass independently.
- [ ] Browser rendering/accessibility and catalog reconciliation are separately reviewed.

Until the applicable gates pass, PR #406 remains draft/unmerged and production remains protected.
